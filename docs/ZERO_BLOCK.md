## Architecture decision (Z0)

A `zero-block` is one normal GrapesJS section with a stable `attributes.id`, an empty `components` collection and one `zeroData` object. There is no second project, database table, DOM component tree, AI document or publication pipeline. The additive component contract keeps the outer `{schemaVersion:1,engine:"grapesjs",data:ProjectData}` envelope. `zeroData.version=1` is mandatory; unknown versions fail closed. A future incompatible change must supply an explicit version migration. Existing non-Zero documents require no migration.

`zeroData` contains 1–10 artboards and a bounded tree of typed elements. New blocks start with five default artboards; users may add or remove modes and choose unique widths from 320 to 2400 px. The widest mode remains the base (`desktop` identity); deleting it promotes the next widest mode and materializes its resolved element values into the base without changing layout. Adding a new mode copies the nearest wider mode. Adding above the current base snapshots the old base into a generated `bp-*` mode. Types: text, image, rectangle, ellipse, line, button, group, `html`, `tooltip`, `vector`, `video`, `form` and (since 00.00.129) `gallery`. These are additive element types within `zeroData.version=1`, not a replacement of the Project Data envelope or a migration; existing blocks remain unchanged. Text is plain text or an array of safe marked runs (`text`, boolean `bold/italic/underline`), not HTML. Groups alone can have children. IDs are unique within each block and renderer CSS is scoped by the containing component ID, so whole-block copies remain isolated.

Authoritative validation: `backend/ZeroBlock.php`, called by `Document::validate`. JSON Schema mirrors the structural contract in `schemas/project.schema.json`; runtime validation also enforces uniqueness, total node count, depth, URL parsing, finite numbers and byte limits. Limits: 300 elements, eight group levels, 256 KiB per block, coordinates/rotation within ±20000, positive sizes up to 20000. The existing project-wide 2 MB and complexity limits still apply. Style keys, colours, font names, anchors, containers, tags and URL schemes are allowlisted. Arbitrary SVG, scripts, HTML embeds and animation payloads are not accepted as Zero elements.

## Coordinate contract

All element positions are absolute. A section has independent height, `position:relative`, `width:100%` and a selectable overflow policy. Every object, including a child of a group, has independent X/Y/W/H, rotation, container, anchor X/Y and origin X/Y. Negative offsets and overlap are supported. Array order defines deterministic sibling z-index; a group is its own stacking context. No Flex/Grid document flow is used to place Zero elements. Flex/Grid in the surrounding app UI or ordinary GrapesJS sections is unrelated to this engine.

For a container of size C and an element of size S:

```
pivot = containerStart + anchor * C + offset
localMatrix = translate(pivot) * rotate(angle) * translate(-origin * S)
worldMatrix = parentWorldMatrix * localMatrix
```

Anchor/origin components are 0, 0.5 or 1. Changing anchor, origin or Grid/Window container adjusts offsets to preserve the rendered position, including rotated elements. A group supplies its own local width/height; its children do not reference the outer page. Group/ungroup converts all five modes while preserving world matrices. Group resize scales local geometry and typography; image/group proportions can be preserved. Zoom and pan belong only to the camera, never to saved coordinates.

At the top level, Window is the full-width section viewport. Grid is a centered coordinate region of `min(section width, gridWidth)`; it is not CSS Grid. Its default desktop width is 1200 px. Grid columns, margins, gutter, rulers and guides are editor aids. The published renderer never emits them.

JS geometry: `src/zero/model/model.js`; affine matrices and group scaling: `transforms.js`; structural operations: `operations.js`. Pure tests compare JS and PHP geometry for every mode and verify rotated anchor/group transformations. The frontend `renderZero` and PHP `ZeroBlockRenderer` use the same formula and media boundaries. Normal typed elements render as standalone HTML/CSS; the explicit HTML element below can run author-provided JavaScript only inside its isolated iframe.

### HTML element sandbox (00.00.123)

The HTML element is an additive type within `zeroData.version=1`. Its only additional field is `code: {html, css, js}`; the server enforces exact keys, string types, UTF-8 byte limits for each field and in total, and rejects CSS that could close the renderer's `<style>` boundary. The JSON Schema mirrors this contract. Source remains Project Data; PHP never executes it.

The editor and PHP renderers keep the `sandbox` attribute present and omit `allow-same-origin`, forms, popups and top-navigation permissions. JavaScript runs in the editor only in Preview. If the JS field is empty, `sandbox=""` retains the sandbox restrictions and disables scripts. Static output allows scripts only when the saved JS field is nonempty. A per-document nonce permits a small bootstrap to transport JS as base64 data and insert it within the isolated frame. The local app router generates a fresh nonce per editor-shell response and exposes it in a meta tag; the `srcdoc` frame reuses that nonce because CSP Level 3 inherits the parent policy for `srcdoc`. The parent and child policies therefore authorize the bootstrap without adding `unsafe-inline` to `script-src`. The frame CSP blocks `fetch`/WebSocket and external scripts, frames, images, fonts and media; data/blob images and inline styles are allowed. The frame has an opaque origin, cannot access editor DOM, cookies or local storage, and cannot submit forms, open popups or navigate the top-level page. Script can navigate its own iframe, but cannot use it to access the parent page. These measures isolate code; they do not sanitize or audit it. Authored JavaScript can still consume CPU. Only execute code the project owner trusts.

### Vector element (00.00.126)

Vector stores only an `icon` key from a curated allowlist present in the checked-in Tabler catalogue. It does not accept SVG, HTML, path data or JavaScript from Project Data. The editor Inspector selects among the same keys; the frontend and PHP renderers insert only the trusted local SVG source, with the layer name as its accessible label. The CSS sizes the icon within the element's absolute geometry and inherits its color. Schema and PHP validation require the key on Vector and reject it on other element types. The same markup is used in the editor, saved preview, static ZIP and public snapshots; no CDN or runtime dependency is required.

### Tooltip element (00.00.125)

The Zero palette adds a `tooltip` element with a question-mark button and a plain-text description edited from the Inspector. `content` is required and capped at 2,000 characters in both the JSON Schema and PHP validator. The JS and PHP renderers escape it and output an accessible `aria-describedby`/`role="tooltip"` pair; CSS reveals the text on hover and keyboard focus. No authored HTML or JavaScript is evaluated for this type. Tooltip styles are emitted only for documents containing one and use matching selectors in the editor, saved preview, static ZIP and public renderer.

### Video element (00.00.127)

The Inspector accepts standard YouTube watch/short/embed and Vimeo URLs, but never provider embed HTML. The client canonicalizes recognized IDs to `https://www.youtube-nocookie.com/embed/{id}` or `https://player.vimeo.com/video/{id}`; PHP validation rejects other hosts, schemes, credentials, explicit ports, fragments, malformed IDs, and a `videoUrl` field on non-video types. JSON Schema mirrors the type/field contract. Both renderers emit a titled, lazy iframe with a restrictive sandbox and `referrerpolicy="no-referrer"`. The editor app CSP and exported page CSP allow only those two exact iframe origins; pages without a Zero Video do not receive external frame permissions in export. Video is rendered consistently in editor, saved preview, ZIP and public snapshot, with an inert placeholder when no URL is configured. Playback depends on provider privacy/availability and network access.

### Form element (00.00.128)

Form is a layout-only element with 1–8 typed fields (`text`, `email`, `tel`, `textarea`), bounded labels/placeholders and a button label. It is intentionally rendered as a `role="group"` container rather than a `<form>`; controls are read-only, the button is disabled, and a note says submission is not connected. No user data is collected or sent, and the schema/PHP validator reject unknown field properties such as `action`. The editor renderer and PHP renderer share the inert behavior for the canvas, saved preview, ZIP and public snapshot. A real form endpoint, submission handling, spam controls and storage are not part of this element and must be implemented separately before enabling submissions.

### Gallery element (00.00.129)

Gallery is one typed, absolutely positioned Zero element containing up to 12 image records. Each record has a unique bounded ID, a safe image `src` and escaped alt text. Private image URLs use the existing project Asset API and are checked by the existing owner policy; HTTPS URLs remain allowed. The inspector adds, replaces, removes and labels images from the project library and edits `columns` (1–6), `gap` (0–80 px) and `objectFit` (`cover`/`contain`). Each breakpoint keeps its own normal Zero geometry. The inner photo arrangement is a grid inside the absolute Gallery box; it does not change the Zero Block document flow. Columns are capped to 2 at the tablet artboard widths and 1 at widths up to 480 px, also capped by image count. Images are lazy-loaded and their corner radius matches the Gallery's radius. Both renderers emit only fixed, escaped `figure`/`img` markup and scoped CSS; no user code or scripts run. Saved preview embeds private photo bytes, while ZIP/publication use the existing managed-media packaging path.

## Responsive contract

| Default mode | Reference width | Default published range |
|---|---:|---|
| desktop | 1200 | 1200 and wider |
| laptop | 980 | 980–1199 |
| tablet | 640 | 640–979 |
| landscape | 480 | 480–639 |
| mobile | 360 | below 480 |

Reference widths are not media boundaries. With custom widths, modes are ordered by width and each non-base mode ends one pixel below the next wider mode. The toolbar displays each mode as a Tabler device icon; the settings popover lists the same icons, editable widths, add/remove actions and Save. Widths must be unique; the base remains widest; at least one and at most ten modes are allowed. Desktop properties form the base; each other mode overlays only its own geometry/style/visibility/source properties. Overrides do not cascade through another smaller mode. Artboards independently store height, background, grid width, margin, gutter, overflow and guides. Content, rich text and links are shared; image source, visual styles and geometry can differ by mode. `<picture>` handles responsive source selection in static output.

Inspector markers: `↳` inherited, `•` overridden. Reset removes the current element's mode override. Initial adaptation scales only elements without an existing override, preserving existing values. Group/ungroup materializes per-mode geometry to preserve placement; users can reset an override before requesting initial adaptation. Mobile never becomes a vertical Flex layout.

## Save and synchronization

Entry: `/projects/:projectId/pages/:pageId/zero/:blockId/edit`. The section card, selected-section button and double click open a named separate window after saving the main editor. The main editor treats its content as opaque and cannot drag internal objects with GrapesJS handles.

`PUT /api/projects/:projectId/pages/:pageId/zero/:blockId` accepts exactly `{version,zeroData}`. Normal session, owner and CSRF checks apply. The server resolves the page and unique component ID, validates Zero data, replaces that block in a copy of Project Data and calls the existing `Store::save`. Asset ownership, expected-version CAS, settings reconciliation and revision creation are unchanged. `update_zero_block` is also available through the existing typed operation service; future AI/MCP commands must use the same validated canonical model, not a parallel tree. No new AI Engine was added.

Completed operations debounce autosave. Pointermove updates the local model and only affected DOM styles through requestAnimationFrame; it does not send network mutations or rebuild all images. A continuous gesture records one history entry. Selection handles occupy an editor-only overlay above all element stacking contexts.

BroadcastChannel messages contain project/page/block IDs and revision only. The server remains authoritative. A clean main editor reads the saved version and patches only the target model; changes elsewhere trigger a clean reload. Dirty or in-flight main edits are retained and produce an explicit conflict. A 409 in Zero Editor retains the complete local model and exposes JSON download. Rebase is safe only when the remote block is still identical to the originally loaded block; otherwise loading the remote model needs an explicit discard confirmation. Main dirty tracking compares the accepted GrapesJS serialization snapshot, avoiding normalization-driven save loops.
