# AI Engine

## Addressed edits in the editor · version 00.00.030

The inspector's AI edit works on exactly the selected GrapesJS component. Before the provider request, the editor saves pending work and sends the prompt, page ID, a page-relative component path, any already-persisted component ID, and the current project version. It sends a small projection of the selected component: type/tag/name, allowlisted local styles and, for text components, plain text. It does not send the rest of the page or descendants as editable targets. Existing component text is untrusted input; the system prompt instructs the model to ignore instructions inside it.

When a selected component has no persisted ID, the server resolves the path against the owner's current saved Project Data and assigns a random `cmp-*` ID only in a cloned candidate document. The candidate ID is returned with the non-mutating proposal; cancellation or provider failure creates no project revision and does not save the ID. If an existing ID was supplied, the server checks that it still identifies the component at that path. Project owner, CSRF, rate limit and expected-version checks run before provider access.

The response schema permits only `replace_text` for selected text components and allowlisted `update_styles` for the selected component ID. The server replays these typed operations through Project Data validation on its candidate clone, and the browser validates that every returned operation targets the same selected model. The UI presents a before/after preview and asks for explicit confirmation. On confirmation, it attaches a newly assigned ID if needed, applies only the approved text/styles through GrapesJS Core, and saves through the normal Project Data envelope and optimistic version flow, creating one ordinary revision. Text replacement removes old nested text and stores a single plain-text GrapesJS textnode while preserving the selected element's attributes and styles. Any editor change invalidates a pending proposal.

Fixture and API tests cover an ID-less target, path/ID mismatch, ownership, CSRF, stale version, invalid operations and non-mutating proposal preparation. Browser save/reload was verified separately with a normal editor change: revision 19 → 20, followed by reload and confirmation that the text and persisted component ID remained. A live AI edit did not reach proposal preview: the active free OpenRouter model returned a temporary provider-unavailable error, so AI preview → confirm → save → reload remains unverified. The provider response remains probabilistic: structured output and validators enforce the supported operation contract, while task-specific quality requirements still need explicit acceptance checks.

## Профили OpenRouter · версия 00.00.020

Владелец проекта может создать несколько OpenRouter профилей с собственными именами, API-ключами и ID основной модели. Владелец может настроить необязательную резервную модель в том же профиле. В списке можно выбрать активный профиль, изменить его или удалить. AI-планирование использует активный профиль; при удалении активного автоматически выбирается другой сохранённый профиль, а при удалении последнего AI отключается. При редактировании пустое поле ключа сохраняет прежний ключ, пустое поле резервной модели отключает fallback.

После одной повторной попытки основной модели на временной сетевой ошибке, HTTP 408/429 или 5xx сервер отправляет тот же структурированный запрос через указанную резервную модель с тем же API-ключом. Ошибки авторизации и валидации не переключают модель. Каждый вызов может тарифицироваться отдельно по правилам OpenRouter; интерфейс показывает обе модели и предупреждает о возможной дополнительной стоимости. Резервная модель хранится в `project_ai_profiles.fallback_model`; миграция v6→v7 оставляет её пустой для существующих профилей.

API-ключ вводится в парольное поле и шифруется сервером через libsodium secretbox. Браузер получает только ID профиля, название, модели и признак активного профиля; значения ключей никогда не возвращаются. Секреты хранятся отдельно от Project Data, общих настроек и ревизий и не выводятся в application logs. Миграция schema 4 переносит прежний ключ в профиль «Основной профиль», сохраняя шифротекст, модель и optimistic version.

Шифровальный ключ приложения создаётся рядом с SQLite как файл <путь к базе>.ai-key с правами 0600; каталог базы и sidecar должны находиться вне public/ и быть доступны только PHP service user. Для восстановления AI-профилей нужны SQLite и этот файл. Если sidecar утрачен, приложение не создаёт новый ключ шифрования поверх прежних данных: владелец должен ввести API-ключи заново. Ключи OpenRouter не читаются из окружения и не включаются в резервный JSON проекта.

GET /api/projects/{id}/ai/settings возвращает список профилей и безопасный статус активного. Создание, редактирование, выбор активного и удаление доступны через POST /api/projects/{id}/ai/profiles, PUT/DELETE /api/projects/{id}/ai/profiles/{profileId} и POST /api/projects/{id}/ai/profiles/{profileId}/activate. Все изменения требуют авторизации владельца проекта, CSRF и ожидаемой версии общего списка профилей. Старые PUT/DELETE /ai/settings остаются совместимыми с прежним single-profile UI. Endpoint плана POST /api/projects/{id}/ai/design-plan использует только текущий активный профиль.

## Собственный текст в готовых секциях · версия 00.00.021

Design-plan возвращает обычные текстовые значения для фиксированных текстовых полей девяти встроенных секций. Каждый ответ привязан к section ID и к заранее заданному порядку полей локального preset; сервер проверяет наличие ровно одного набора на каждую выбранную секцию, точное число строк, длину до 220 символов и отсутствие HTML/разметки, управляющих символов и URL. Браузер повторяет валидацию и вставляет только `content` в известные text/link компоненты. Никакие AI-HTML, CSS, атрибуты, компоненты или операции напрямую не принимаются.

До подтверждения UI показывает весь сгенерированный текст рядом с планом. После подтверждения его можно редактировать обычными средствами GrapesJS; типизированные операции проходят owner/CSRF/version и Project Data validation и записываются одной обычной ревизией. Максимум ответа OpenRouter для расширенного плана ограничен 3200 токенами. Никакого дополнительного live-вызова при реализации версии 00.00.021 не выполнялось; успешная проверка настоящего провайдера остаётся отдельным пунктом приёмки.

## AI-планирование · версия 00.00.006

В редакторе есть форма design-plan, которая сначала проверяет настройки AI текущего проекта. Если ключ не настроен, кнопка отправки prompt остаётся выключенной, а редактор предлагает открыть «Настройки сайта → AI Engine». Перед запросом UI сообщает, что на OpenRouter уйдёт только текстовое описание и что содержимое страницы/Project Data не передаётся. До нажатия «Составить план» описание не отправляется.

Проверенный ответ отображается в preview: тип сайта, аудитория, цель, стиль, восемь цветов, список секций, заметки по адаптивности и доступные model/usage/cost metadata. Frontend повторно ограничивает план фиксированными section IDs и hex colors. Применение требует отдельного подтверждения и создаёт только `create_component` операции из локальных библиотечных presets. Никакой AI HTML/CSS/JSON напрямую не сохраняется. Серверный `/operations` повторно проверяет owner, CSRF, expected version, allowlists и весь Project Data, затем создаёт одну обычную revision.

Секции добавляются в конец выбранной страницы, текущий контент сохраняется. Цвета из AI-плана применяются только к новым секциям; типографика и radius наследуются от текущей темы проекта. Глобальные design tokens и существующие блоки не меняются.

## Параметры запросов и границы

Ответ запрашивается через OpenRouter Chat Completions с `response_format.type=json_schema`, строгой схемой, `provider.require_parameters=true` и `usage.include=true`. Лимит 3200 выходных токенов передаётся в `max_tokens`, чтобы соответствовать параметру, который широко объявлен в метаданных моделей и требуется для совместимой маршрутизации. Сервер повторно проверяет результат. Каждый запрос к модели ограничен 25 секундами и 1 МБ ответа; на одну PHP-сессию допускается до пяти вызовов за минуту. Это защита от случайного повтора, а не денежная квота. Основная модель повторяется один раз после временной ошибки или HTTP 408/429/5xx; после неудачи сервер вызывает настроенную резервную модель максимум один раз с теми же ограничениями. Поэтому общий лимит выполнения PHP для AI endpoint — 120 секунд, чтобы обработать обе попытки и необязательную резервную модель без обрыва HTTP-соединения. Ошибки авторизации и валидации не повторяются через fallback.

В версии 00.00.020 из редактора отправлен только синтетический prompt с профилем `openrouter/free`; интерфейс ответил «AI-провайдер временно недоступен», предпросмотр не появился. В версии 00.00.022 live-запрос с активным профилем создал валидный preview восьми секций (2815 выходных токенов, стоимость по ответу провайдера — $0.000000); проект остался на ревизии 0. Подтверждение применения, save/reload и публикация не выполнялись. Получение списка моделей, production per-user quota, денежный лимит и мониторинг расходов ещё не реализованы. Внешние запросы требуют HTTPS на deployment и явного действия пользователя в AI-панели.

В версии 00.00.022 проверка выявила, что активная модель объявляла `max_tokens`, тогда как приложение отправляло `max_completion_tokens` при `require_parameters=true`; запрос переведён на заявляемый моделью параметр. PHP теперь получает 120-секундный бюджет для retry/fallback. Ранее PHP завершал запрос на 30-секундном лимите во время второй попытки, из-за чего браузер показывал сетевой `Failed to fetch`. Локальный сервер также был остановлен; `npm run serve` снова поднял постоянный адрес приложения.

## Генерация полноценной страницы · версия 00.00.023

В редакторе AI-дизайн теперь генерирует HTML-фрагмент и responsive CSS для страницы, а не только выбирает встроенные секции. На OpenRouter отправляется лишь явно введённое описание; Project Data и текущее содержимое страницы не передаются. Строгая схема возвращает от 3 до 9 секций, один hero, цель и визуальное направление. Сервер парсит HTML, разрешает ограниченный набор тегов и атрибутов, отклоняет скрипты и event handlers, проверяет CSS по allowlist свойств/значений, разрешает только классовые селекторы, сверяет классы с разметкой и добавляет случайную область CSS. ID и ссылки внутри страницы переименовываются в ту же область. Внешние ресурсы и JavaScript не принимаются.

До импорта UI показывает результат в отдельном sandbox iframe с CSP без скриптов, сетевых запросов, изображений и шрифтов. Пользователь отдельно подтверждает добавление секций в конец выбранной страницы. Редактор создаёт обычные редактируемые GrapesJS components и CSS rules; сохранение идёт существующим owner-authenticated Project Data envelope, CSRF, CAS/version и revision flow. Изображения, формы, произвольный JavaScript и custom embeds эта версия не генерирует. Пер-профильный ключ остаётся в AI Engine, никакие секреты не читаются из env.

Лимит ответа генератора — 6000 токенов; prompt ограничен 4000 символами, на сессию действует общий лимит до пяти AI-вызовов за минуту. Fixture tests проверяют импортные поля, namespacing и отказ от небезопасной разметки/CSS; HTTP tests проверяют авторизацию, ownership, CSRF, размер/форму prompt и отсутствие вызова без credentials. Реальный OpenRouter-вызов и нажатие «Добавить дизайн» в этой версии не выполнялись: они остаются отдельной live-проверкой с потенциальной стоимостью провайдера.


## Пользовательские Skills · версия продукта 00.00.034

Владелец проекта управляет библиотекой до 10 Markdown Skills в «Настройки сайта → AI Engine». Сохранение, редактирование, активация и удаление требуют актуальной версии библиотеки и проходят проверку владельца и CSRF. В полный AI-запрос включаются текст Skill и ручной чек-лист только когда пользователь выбрал этот профиль и нажал генерацию; Project Data и содержимое редактора не отправляются. Сценарии и код, описанные внутри Skill, не исполняются.

Перед импортом редактор требует отметить каждый пункт чек-листа. Это пользовательская проверка, а не автоматическое доказательство соблюдения требования. Сейчас универсальные семантические критерии из произвольного Skill не преобразуются в validators и не проверяются моделью/сервером с доказательствами. Для более строгого агента остаются нужны типизированные проверяемые правила, traceability результата, bounded repair/evaluation и отказ при непроверяемых требованиях.
