# Модель данных v1

Envelope: `{schemaVersion:1, engine:"grapesjs", data: ProjectData}`. Структурная JSON Schema — schemas/project.schema.json; authoritative runtime validation and security policy — backend/Domain.php::Document::validate. API разбирает и возвращает JSON-объекты с сохранением различия между `{}` и `[]`, в том числе при сохранении и чтении документа. Версия API и версия документа различны: `version` — optimistic concurrency counter, `schemaVersion` — формат.

`data.pages[]`: стабильные id/name, один frames[] на страницу; frame.component — wrapper, вложенные components, head/docEl служебные элементы Core. `data.styles[]` содержит selectors, style, mediaText; responsive CSS не преобразуется. `data.assets[]` сохраняется вместе с проектом. Для управляемого изображения компонент `src` может хранить только `/api/projects/{projectId}/assets/{assetId}/file`; сервер требует, чтобы запись существовала и принадлежала этому же проекту. Байты и метаданные находятся в таблице `project_assets`, не в документе/ревизиях, поэтому envelope schemaVersion остаётся 1. Другие Core metadata сохраняются losslessly при прохождении policy. Нельзя заявлять произвольные Core plugins совместимыми: custom type потребует schema/policy change.

В component definitions сохраняются type/tagName/name/content/attributes/style/components и служебные head/docEl. GrapesJS генерирует component ids и хранит их в attributes.id; round trip не заменяет id. Нативные text/textnode/link/image/default/wrapper и служебные main/head допустимы. Script, script-export, event attrs, srcdoc/srcset/formaction запрещены; tag allowlist ограничен. Произвольные дополнительные metadata сохраняются, чтобы не терять данные Core, но для них также действует рекурсивная политика безопасности. Редактор может показать временное неподдерживаемое состояние, сервер вернёт 422 без записи.

Limits: 1–30 страниц, 1 frame/page, 2 МБ сериализованного документа, глубина 45, обход не более 50 000 значений. HTML content — только базовое inline formatting. URL — HTTPS/якорь/mailto/tel, CSS url()/@import запрещены. Удалённые ресурсы не проксируются сервером. Свойства layout используют CSS display:flex/grid, gap, padding и responsive rules; отдельного layout AST нет.

PUT body: `{version: currentVersion, document: envelope}`. Сервер сначала проверяет owner и документ, затем внутри транзакции выполняет UPDATE WHERE version=?, increment и INSERT revision. Конфликт возвращает 409; нет overwrite/автоматического merge. Невалидный документ не меняет ни текущую версию, ни историю. Данные и ревизия коммитятся вместе. У каждого проекта хранятся последние 200 ревизий; UI запрашивает максимум 50. POST `/projects/{id}/revisions/restore` принимает `currentVersion` и `targetVersion`, валидирует сохранённый документ и CAS-обновляет проект новой версией, не переписывая выбранную ревизию. SQLite migration runner последовательно доводит базу до schema v6; Project Data migrations по-прежнему требуют явной отдельной версии и тестов обратной совместимости. Undo stack не сериализуется: это отдельная от revisions история открытого редактора.

`POST /api/projects/{id}/operations` принимает `{version, operations}` с 1–20 действиями над stable component IDs. Поддерживаются `create_component`, `rename_component`, `update_content`, `replace_text`, `update_styles`, `update_layout`, `delete_component`, `duplicate_component`, `move_component`, `reorder_component` и `update_zero_block`. Создание в page root использует `parentId: "page:<page-id>"`; новые узлы получают уникальные `attributes.id`, если id не задан. Переименование ограничивает название 1–100 символами без управляющих символов. Удаление требует поля `confirm: true`. Дублирование назначает новые стабильные ID потомкам, переназначает внутренние fragment/IDREF ссылки и копирует CSS rules с remap ID selectors; корневые компоненты страницы дублировать нельзя. Zero Block обновляется только целым типизированным `zeroData` с page/block IDs. Каждый шаг проходит allowlist и повторный `Document::validate`; после успешной пачки API сохраняет результат через CAS и создаёт одну новую revision. Ошибка, stale version или чужой project ID не меняют документ и историю. Операции пока не покрывают весь редактор: например, универсальное изменение всех атрибутов, вставку произвольных компонентных типов и автоматическую миграцию схемы.

## Настройки проекта

Project site settings are separate from the canonical Project Data envelope and use `projects.settings_payload` schema version 4. Each stable page id carries its route slug, home flag, and SEO defaults/overrides (`title` up to 70 characters, `description` up to 160, `robots` limited to `index` or `noindex`, and optional HTTPS `socialImage` up to 2048 characters). Server validation, project ownership, CSRF, and the expected document version protect settings updates. The same settings envelope is stored with each revision, so restore returns matching page metadata. Upgrading settings schema 3→4 adds defaults without changing the SQLite schema or Project Data JSON. SEO metadata and design tokens are included in static ZIP export.

`GET /api/projects/{id}/export/static` authenticates the session and checks project ownership, then exports only the currently saved document/settings. It writes `index.html`, one `{slug}/index.html` per secondary page, shared `assets/site.css`, and referenced raster images under `media/` into an in-memory ZIP response; the project document and revision history are not modified. The static renderer consumes settings schema v4 SEO and design tokens, applies a strict component/tag/attribute/CSS allowlist, escapes text/metadata, emits no scripts, and rejects unsupported media-query syntax. The downloadable artifact does not mutate the document or publish automatically; explicit online publication is described below.

## Импорт и миграции

Сейчас доступен только JSON export; API/UI импорта нет. Когда он появится, принимается только полный envelope с известными `schemaVersion` и `engine`. Неизвестная версия не угадывается и не подменяется текущей. Для каждой версии-источника нужна отдельная детерминированная миграция `N → N+1`; после неё документ повторно проходит актуальные structural и security проверки. Без явной миграции несовместимая версия отклоняется с 422, без создания проекта, записи или ревизии. Импорт существующего проекта обязан использовать expected version и сохранять поведение CAS; никакого force overwrite или автоматического merge. Для импорта потребуются valid fixtures каждой поддерживаемой версии, invalid/security fixtures, тесты миграции и доказательство, что отказ не меняет данные.

Редактор запускает PUT через debounce после 1,4 секунды без изменений и повторяет сетевые ошибки/ответы 5xx через 5 секунд. Конфликт версий блокирует дальнейшую запись, пока пользователь не загрузит серверную версию; локальное состояние остаётся доступным для JSON export. Другие ошибки 4xx не повторяются автоматически. Перед переходом к dashboard редактор пытается сохранить изменения и спрашивает пользователя, если сохранение не удалось.


## Публикации

SQLite schema v4 introduced `publication_versions`; as of schema v6 snapshots store a map of allowlisted static paths to UTF-8 contents or validated base64 raster data, alongside publication number, source `documents.version`, and timestamp. `project_publications` хранит только указатель на активную версию; composite foreign key не допускает привязать снимок чужого проекта. Publish требует authenticated owner, CSRF и совпадающий expected project version, повторно вызывает server-side static renderer и атомарно записывает новый snapshot/pointer. Unpublish удаляет pointer, но оставляет все snapshots; последующая публикация увеличивает publication version.

Публичный host `project-id.<JUZIMDER_PUBLIC_HOST_SUFFIX>` использует отдельную ветку PHP router до запуска admin session. Он отдаёт `/`, разрешённые slug routes, `/assets/site.css` и только raster media paths из активного immutable snapshot; API, исходная SQLite и незапубликованные файлы недоступны. Response включает restrictive CSP, no-store и same-origin media. Локальный suffix по умолчанию — `juzimder-ai.localhost:8080`; production требует wildcard DNS/TLS и изолированного admin hostname. Preview candidate реализован; rollback UI и custom domains пока не реализованы.


## Component extension: zero-block / zeroData v1

Envelope schemaVersion остаётся 1; явное additive расширение допускает type zero-block с обязательным stable attributes.id и одним zeroData.version=1. Core components/content этого блока пусты. zeroData содержит пять artboards и typed elements с geometry/style/overrides; children допустимы только у group. Структурная JSON Schema и backend ZeroBlock::validate согласованы; backend дополнительно проверяет суммарные quotas, IDs/depth/finite values/URL. Managed src во всех responsive overrides участвуют в прежних asset ownership checks. Смена несовместимой версии потребует явной migration; неизвестные версии отклоняются. См. ZERO_BLOCK.md.
